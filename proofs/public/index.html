In one paragraph

What Wise is.

Wise is a small protocol. A signing key seals a file: the seal contains a fingerprint of the file's bytes plus the key's signature plus a timestamp. That seal travels with the file forever. Anyone who later receives the file can drop it on the verifier and get a one-word answer about whether the file is the same bytes the key sealed.

The signing key may be local (generated on a device you control), named (with a self-declared display name), or trusted (matched against a list of known keys the receiver chose to trust). The protocol does not promise anything about the real-world person, company, or organization behind a key unless the receiver has explicitly chosen to trust that key by fingerprint.

The three results

What the verifier tells you.

Drop a file on the verifier and you get exactly one of three answers. No maybes. No confidence scores. No fifth state.

Verified

The file matches the proof inside this .win container. No byte changes detected. The signing key on the seal is shown alongside, with its trust class — local, named, or trusted — so you can decide what the signature means to you.

Tampered

The file no longer matches the proof inside this .win container. At least one byte changed since sealing.

Invalid

This .win container is not valid or cannot be verified — malformed structure, broken signature, or unparseable proof.

Honesty first

What a .win does not prove.

This is the part most provenance systems oversell. Wise will not.

It does not prove who is behind the key

A signing key is a number. The key signed the file. Whether the human, company, or device behind that key is who they claim to be is a separate trust question — answered only if the receiver has explicitly added the key fingerprint to a local trusted list.

It does not prove the file is true

A .win can seal a lie just as easily as a truth. All it proves is that the file existed at a moment, unchanged since, signed by a specific key. It says nothing about whether the contents are correct.

It does not prove the author wrote it

The signing key sealed bytes. The key did not see who wrote them. A sealed essay proves the essay existed at a time, not that the person who sealed it is the author.

It does not prove the file is original

Someone could copy a file and seal the copy. The seal is real; the originality claim is not part of it.

Wise.Est Systems did not automatically sign your file

Each .win is signed by whichever key sealed it — typically the local key generated on the user's own machine. There is no central Wise.Est Systems signing key in this protocol. If you ever see a result that says "signed by Wise.Est Systems", it is true only because the signing key matched a fingerprint the receiver explicitly added to their trusted list.

It does not depend on us being alive

If Wise.Est Systems disappears tomorrow, every .win ever sealed still verifies. The proof is mathematical, not organizational. This is the whole point.

Honest notes about how this works

There is no central Wise.Est Systems witness key. The protocol does not have an "official Wise.Est key" that signs your file. Each .win is signed by a key generated on the device that sealed it. That key may be local-only, named, or one a receiver has explicitly added to a trusted list — but never assumed-trusted by default.

Trust classes the verifier shows. A signing key is one of: Local (signed by a fresh key generated on the device), Named (the key declares a display name; the receiver still chooses whether to trust it), Trusted (the key fingerprint matches an entry the receiver added to their local trusted list), or Unknown (valid signature, no further trust signal). Verification proves the file matches what the key signed; the trust class tells you what that signature means.

A hardware key is being designed. A small device that holds a non-extractable signing key — your own, not anyone else's. Each device's key is itself just another key; receivers decide whether to add its fingerprint to their trusted list. The protocol does not assume hardware keys are trusted by default.

Sealing is not yet open to the public. Right now you can only verify .win files, not produce them. The sealing flow is being built. When it ships, every seal will be signed by a key generated on the user's own device.

Read the protocol. Source and specs at github.com/Wise-Est-Systems. Built to be implementable from scratch by anyone — so it survives us.
