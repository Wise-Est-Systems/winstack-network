In one paragraph

What WIN is.

WIN — the Wise Independent Network. Three commitments in the name: Wise (the family it belongs to), Independent (no organization is needed to verify), Network (no central operator runs it).

WIN gives every file a win tag — a small portable record that travels with it. The tag says when the file was sealed, which key sealed it, and whether the file is unchanged since. Receivers read it offline, with no account and no trusted server. There is one public file type: .win. The proof and the change-map live inside it.

The three results

What the verifier tells you.

Drop a file on the verifier and you get exactly one of three answers. No maybes. No confidence scores. No fourth state.

Verified — bytes match the seal

The file matches the proof inside this .win. No byte has changed since it was sealed, and the signature is intact. The signing key is shown alongside, with a receiver-local label, so you decide what the signature means to you.

Tampered — a byte changed

The file was sealed once and has been altered since. The file's SHA-256 no longer matches the hash recorded in the tag. The original is gone.

Invalid — the proof can't be verified

The .win is broken or unreadable — a signature that won't verify, an unparseable container, a missing magic header, a time chain that won't link, or a bad policy proof. The seal could not be trusted or read.

The claim, exactly

What a .win proves.

A verified .win establishes a layered claim — and not one inch more:

  • Bytes — the file's bytes match the SHA-256 digest recorded in the proof
  • Signing key — a specific Ed25519 keypair signed that proof
  • Self-declared name — the signer may attach a display name; the verifier shows the claim, it does not validate it
  • Lineage — the file may carry a verifiable version chain (parents, generations, key delegation)
  • Anchored time — if RFC 3161 anchoring was used, an independent timestamp authority confirms the hash existed at that moment
Honesty first

What a .win does not prove.

This is the part most provenance systems oversell. WIN will not.

  • Who is behind the key — the real-world person, company, or device
  • That the signer told the truth
  • That the file's content is factually correct
  • That Wise.Est Systems signed it — there is no central key
  • That it is the first copy ever made — only the first in this lineage
  • That a local timestamp is globally authoritative — only RFC 3161 anchors are independently verifiable

That honesty is the point. A .win can seal a lie just as easily as a truth — all it proves is the bytes are unchanged since a specific key sealed them.

Keys, not identities

Trust & identity.

Witnesses generate and hold their own Ed25519 keys. Wise.Est Systems does not store keys, does not run accounts, and is not contacted during verification — the public key is read straight from the win tag. Whether the human behind a key is who they claim is a separate trust question.

Local

Signed by a key generated on a device — often the receiver's own. Proves the file still matches what that key sealed; not a real-world identity.

Unknown

A valid signature from a key not on any list you keep locally. Real signature, unrecognized signer.

These labels are assigned by your own machine, never enforced by the protocol. Larger witnesses can use signed key-delegation chains to rotate keys without invalidating prior tags. There is no "Official" trust class today — verified real-world identity and official witnessing are the future paid layer, not a claim made now.

The wire format

The .win container.

One binary container. Magic header, the original file carried whole, then the proof as JSON to end-of-file:

[4 bytes] magic: WIN\x01 [4 bytes] filename length (u32, little-endian) [N bytes] filename (UTF-8, no path separators, ≤ 4096 bytes) [8 bytes] file length (u64, little-endian) [M bytes] original file (raw, uncompressed) [rest] proof JSON (UTF-8, to EOF)

Inside the seal

payload_hash
SHA-256 of the file — 64 hex chars. Always SHA-256.
object_signature
Ed25519 over the canonical JSON payload — 128 hex chars. Keys are 32 bytes (64 hex).
creator_identity
The signer's identity record (and any key-delegation chain).
time_event
Local (device clock, default) or External — an RFC 3161 TSA token + anchored time.
policy_proof
Signed proof that a policy evaluator permitted the seal (Permit/Deny).
lineage
parent_ids, lineage_id, optional delegation — the verifiable version chain.
protocol
"V1" — recorded in every proof. Future versions use a different string.
Where WIN sits

The stack.

WIN is the implementation layer of a three-part system. A kernel defines the rules, WIN enforces them at the verification boundary, and a research layer explains exactly how files differ.

Kernel
WiseOrder

Governs how cognition becomes consequence. Classifies claims into verification regimes and produces auditable epistemic artifacts. Not a model, not a network service — it defines the rules WIN enforces. (wiseorder-protocol)

Implementation
WIN — files that prove themselves

The .win format, the crypto layer, the native + WebAssembly verifiers, the desktop drop-target, and the CLI. The part you touch. (winstack-network)

Research
WISEATA — how things differ

Deterministic structural analysis. A proof (.wiseproof) and an expansion (.wiseexp) that show not just that two files differ but how — byte, positional, frequency, transition, and structural layers. (wop)

How it checks

Verification.

The verifier is a pure function — same input, same result, no I/O, no network. It runs in your browser via WebAssembly: files never leave your device, there is no signup, and nothing contacts our servers in the verification path. The same verifier crate compiles to native and to the .wasm that powers every browser surface.

A verified .win passes a 12-step pipeline, in order: protocol version → payload hash → size bounds → object signature → creator identity → module validation → origin consistency → AI-generation record (if present) → import declaration (if present) → time event + chain linkage → policy proof → lineage links, cycle detection, RFC 3161 token, and proof-chain linkage. Any failure that isn't a clean hash-mismatch resolves to Invalid; a hash-mismatch resolves to Tampered.

Same answer, everywhere, forever

Determinism & conformance.

Same input, same verifier release, same accept/reject — on every host, in every conformant implementation. Non-determinism is treated as a defect, not a feature. Canonicalization is RFC 8785 JCS; the hash is always SHA-256.

WiseOrder Protocol v0.1.0 freezes its conformance suite by fingerprint. Any future v0.1.0 implementation must reproduce these byte-for-byte — a divergence is a non-conformance, not a version bump:

WIN itself ships under hard CI gates on Linux, macOS, and Windows: cargo fmt, clippy -D warnings, the full test suite (189 tests), and a WASM build held under a 1 MB compressed budget. Every verifier crate is #![forbid(unsafe_code)]; win-format has zero dependencies. MSRV: Rust 1.82.

Source & specs.

The honest summary

A .win proves one thing precisely: these bytes are unchanged since a specific key sealed them, at a recorded time. It does not prove who holds that key, or that the contents are true. Verified identity is the paid roadmap — stated plainly, because overstating it would defeat the purpose.
